# Отчёт по коду

Дата анализа: **1 октября 2026 года**. Основа: текущие исходники, шаблоны, стили, существующие тесты и сценарий сборки. Это обзор архитектуры и конкретных точек доработки, не полноценный аудит безопасности или сертификация релиза.

## Архитектура

| Файл / каталог | Ответственность |
| --- | --- |
| `app.py` | Flask, HTML-страницы, JSON API, схема SQLite, проверки значений, логика разделов и маршрутизация команд EVE |
| `launcher.py` | Выбор порта, сервер на `127.0.0.1`, ожидание запуска, окно pywebview и фоновый агент |
| `eve_assistant.py` | Нормализация речи, ключевое слово, разбор команд и выбор вариантов распознавания |
| `eve_agent.py` | Vosk, устройства ввода, фоновый голосовой цикл, адаптер действий ОС |
| `eve_local.py` | Gemini, голосовые профили, загрузка локальных моделей, синтез WAV |
| `eve_speechkit.py` | Отдельный адаптер распознавания и синтеза Yandex Cloud |
| `templates/` | Jinja-страницы, общая оболочка, формы и диалоги |
| `static/js/app.js` | Запросы API, отрисовка разделов, формы, календарь и взаимодействие с голосом |
| `static/css/` | Базовые стили, слой недельного экрана и переопределения по референсу |
| `tests/test_eve_and_utilities.py` | Тесты парсера, провайдеров, команд, финансов и коммунального API |

Поток обычного действия: интерфейс → JSON API → проверка ввода → SQLite → ответ → обновление интерфейса. Для свободного разговора EVE добавляется обращение к внешнему провайдеру; для действий ОС — отдельный адаптер и, в предусмотренных случаях, подтверждение.

## Данные

Схема охватывает задачи, недельные цели, заметки, разделы, месячные приоритеты, финансовые операции, накопления, коммунальные счета и услуги, привычки, настроение, настройки, историю и память EVE.

В `get_db()` включены внешние ключи SQLite, `synchronous=FULL` и ожидание занятой базы до пяти секунд. Соединение хранится в контексте Flask. Индексы созданы для ряда выборок по датам, месяцам и связям. Старые базы обновляются через `ensure_legacy_columns()`.

Деньги хранятся целыми минимальными единицами (`amount_minor`). Для ряда сущностей есть ограничения `CHECK`, уникальность и каскадные связи. Показания счётчиков хранятся как `REAL`; точность расчётов и округления стоит отдельно проверять на реальных тарифах.

## Сильные стороны

- Единая локальная база связывает основные бытовые сценарии.
- Есть отдельные функции проверки текста, даты, времени, суммы, процента и цвета.
- Командный разбор отделён от свободной генерации ответа: модель не получает прямой механизм исполнения произвольного кода.
- Голосовые адаптеры выделены в отдельные модули; недоступность фонового агента не должна блокировать окно планера.
- Существующие тесты проверяют содержательные сценарии, включая подтверждение действий и работу с несколькими коммунальными счетами.
- Пользовательская база и крупные локальные TTS-модели исключены из Git; настройка облачных ключей описана через окружение.
- Есть профили сборки и уведомления о голосовых лицензиях.

## Точки доработки по приоритету

| Приоритет | Наблюдение | Следующий шаг |
| --- | --- | --- |
| Высокий | API не имеет полноценной аутентификации; рядом находятся изменение личных данных и действия ОС | Сохранить локальную модель запуска; отдельно проверить Host/Origin, защиту изменяющих запросов и доступ к действиям EVE |
| Высокий | `python app.py` включает Flask debug, тогда как launcher отключает его | Для обычного использования документировать launcher или Flask CLI без debug; перед распространением пересмотреть точку запуска |
| Высокий | Нет общего механизма пользовательских резервных копий и восстановления в просмотренных маршрутах | Добавить экспорт, восстановление, версию формата и проверку целостности |
| Высокий | Права на весь набор графики и шрифтов не описаны общей лицензией | Провести инвентаризацию перед открытием репозитория |
| Средний | `app.py` около 3005 строк и смешивает несколько предметных областей | Постепенно выделить Flask Blueprints и сервисы данных для задач, финансов, коммуналки и EVE |
| Средний | `static/js/app.js` около 2098 строк объединяет страницы и голосовые состояния | Разделить по областям, сохранив единый API-клиент и общие компоненты |
| Средний | Схема и добавление legacy-полей проверяются при создании соединения | Ввести нумерованные миграции и отдельный шаг обновления базы |
| Средний | Ожидающие подтверждения действия хранятся в памяти процесса | Проверить сроки жизни, повторное подтверждение, перезапуск и привязку к конкретному пользовательскому действию |
| Средний | Несколько файлов CSS накладываются друг на друга, много `!important` | Собрать единые токены и постепенно убрать лишние переопределения |
| Средний | Текущий набор тестов сосредоточен на EVE, коммуналке и накоплениях | Дополнить независимыми сценариями календаря, привычек, миграций и сохранения после перезапуска |
| Низкий | Переменная `--pink` уже хранит синий цвет | Перейти к смысловым именам вроде `--accent`, не меняя поведение интерфейса |

Ограничения выше — задачи для следующего этапа. В рамках оформления репозитория исходная бизнес-логика не изменялась.

## Приватность и интеграции

Локальное хранение и облачный разговор сосуществуют. Gemini получает сообщения и историю; SpeechKit — выбранные аудиофрагменты и текст синтеза. Браузерное распознавание зависит от реализации браузера. Для будущего выпуска нужно проверить, что пользователь видит активный провайдер и может остановить микрофон, отключить память и удалить историю.

Ключи не следует включать в README, примеры, архивы или логи. Проверка списка отслеживаемых файлов не обнаружила баз SQLite, WAV/MP3-записей, PEM-файлов и файлов с именами `*env*`; это не заменяет сканирование содержимого и истории Git на секреты.

## Проверка

Команда существующего набора: `python -B -m unittest discover -s tests -q`. Фактический результат прогона при оформлении см. в [протоколе проверки](VALIDATION.md).

Тесты используют временную базу и подмены внешних интеграций. Даже успешный результат не подтверждает качество микрофона, звучание моделей, доступность облачных сервисов, внешний вид интерфейса или работоспособность собранных приложений на другом компьютере.

## Рекомендованный порядок

Сначала резервные копии и границы доступа к локальному API, затем миграции и разделение крупных модулей, после этого расширение тестов и воспроизводимые сборки. Так архитектуру можно улучшать небольшими изменениями с проверкой существующих сценариев.
